# Deployment and rollback

## Build for the destination

| Destination                        | Build                            | Local preview                      |
| ---------------------------------- | -------------------------------- | ---------------------------------- |
| New GitHub Pages `/apcoseb-clear/` | `npm run build`                  | `npm run preview`                  |
| Root domain `/` (including Vercel) | `npm run build:root`             | `npm run preview -- --base=/`      |
| Other subdirectory `/site/`        | `npm run build -- --base=/site/` | `npm run preview -- --base=/site/` |

All three use `scripts/build.mjs`: legal-source parity, TypeScript, Vite with the requested base, route metadata, then bundle budgets. Deploy the contents of `dist/` at exactly that path. Do not open the output with `file://`. A second build replaces `dist/`; never rebuild while browser tests are using it.

`APCO_PUBLIC_SITE_ORIGIN=https://example.com npm run build:root` writes static canonical and Open Graph URLs for all routes, including the homepage. The variable may also be put in a local `.env` or the hosting build environment. It must be an HTTPS origin without credentials or a path. Client navigation keeps canonical and `og:url` aligned with the current route.

## Hosting

GitHub Pages publication is deliberately manual in the new repository. Pushing to `main` runs validation only; after Pages is enabled, manually dispatch `.github/workflows/deploy.yml` for validate → deploy → production-smoke. The workflow builds at `/<repository-name>/` by default (or `/` for a user/organization Pages repository). Set the repository variable `APCO_SITE_BASE` to `/` for a custom root domain or to an explicit subpath when necessary. This makes the source portable to a new repository without changing component URLs. Success means all three jobs succeeded for the intended commit. Pages canonicalizes directory routes with a trailing slash. Route-specific `index.html` files and `404.html` are generated by the build.

Vercel's root build and `dist` directory are versioned in `vercel.json`; its SPA rewrite remains for client routes. Review deployments may be protected by the hosting project. A READY build alone does not prove browser access or that GitHub Pages finished publishing. Keep temporary share URLs out of committed documentation.

Vercel sets conservative `X-Content-Type-Options`, `Referrer-Policy` and `Permissions-Policy` headers from `vercel.json`. GitHub Pages does not read this config; deploy security headers through the receiving host or edge proxy there. Do not enable an untested restrictive CSP: the page has an inline first-paint theme script and GSAP/Canvas demos. Validate the entire site in a review deployment before applying a host-specific CSP and HSTS policy.

The no-JavaScript search link is generated by the Vite HTML transform from the verified `VITE_APCO_PRODUCT_URL`; it does not need a separate hard-coded origin when the site changes repository or domain.

A custom static server should serve actual files and route directories before the SPA fallback, otherwise it will lose route-specific static metadata. Configure the correct base path and check deep-link refreshes.

## Verify the deployed version

```sh
APCO_BASE_URL=https://example.com/ npm run test:production
```

After manually publishing the new Pages site, use `https://imonsergey.github.io/apcoseb-clear/`. The test URL must end with `/` and match the deployed base. For a locally built custom base, run `APCO_TEST_BASE_PATH=/site/ npm run test:release` after building with `--base=/site/`. This runs the current Chromium release contract; `test:cross-browser` provides the focused three-engine checks.

Before a public launch, confirm product inputs listed in [Handoff](HANDOFF.md), domain metadata, asset usage rights, and real-device behavior. Preview `noindex` in `index.html` and `public/robots.txt` remains intentional; remove it only as part of an approved public launch.

## Rollback

Find the last accepted commit and its successful workflow. Revert the problematic commit(s) on top of current `main` with reviewed `git revert` changes, then pass the same checks and publish normally. Avoid force-pushing shared history. For urgent hosting rollback, select the previously verified deployment in the owner's hosting account and then reconcile Git. Always verify the published content and smoke job, not only the branch SHA.

## Transfer

Use `npm run handoff:package` to export clean committed source without Git history. Initialize a new repository after extraction instead of copying the existing `.git` directory. Preserve dependency locks and third-party notices. Configure destination account permissions, public environment values and CI separately. Do not copy `.env`, authentication material, `node_modules` or local test output.
